# Phase 13: Remove PropTypes - Migrate to TypeScript Runtime Validation

| Field            | Value                                      |
|------------------|--------------------------------------------|
| **Phase ID**     | PHASE-13                                   |
| **Title**        | Remove PropTypes - Migrate to TypeScript Runtime Validation |
| **Stage**        | 3 - Core Library Modernization             |
| **Dependencies** | Phase 8 (defaultProps on function components) |
| **Complexity**   | High                                       |
| **Scope**        | 163 source files with PropTypes assignments, ~1,836 PropTypes references, 133 files using customPropTypes, build pipeline configuration |

---

## Objective

Remove the entire PropTypes runtime validation system from the Semantic UI React source code, including the `prop-types` package dependency, all `Component.propTypes = {}` assignments, all `customPropTypes` utilities, and the Babel plugin that strips PropTypes in production builds. Type safety is preserved and improved through TypeScript interfaces in `.d.ts` files (and eventually inline when sources convert to TypeScript in Phase 14). The `getUnhandledProps` utility, which currently relies on PropTypes-derived `handledProps`, must be updated to use explicit `handledProps` arrays (generated by the existing `babel-plugin-transform-react-handled-props` or declared manually).

---

## Background

### Why Remove PropTypes

1. **React 19 deprecation path.** While React 19 does not remove PropTypes support, the React team has signaled that PropTypes are legacy and TypeScript is the recommended approach. The `defaultProps` deprecation on function components (React 18.3 warnings) is the first step in this direction.

2. **Bundle size.** PropTypes account for significant code volume. With 163 files containing `propTypes` assignments and ~1,836 total PropTypes references, removing them eliminates dead code that is already stripped in production by `babel-plugin-transform-react-remove-prop-types`.

3. **Maintenance burden.** Every prop requires dual maintenance: a PropTypes definition in the `.js` file and a TypeScript interface in the `.d.ts` file. These frequently drift out of sync.

4. **`customPropTypes.js` complexity.** The 370-line `src/lib/customPropTypes.js` implements custom validators (`suggest`, `disallow`, `every`, `givenProps`, `demand`, `multipleProp`, `deprecate`, `contentShorthand`, `itemShorthand`, `collectionShorthand`, `ref`, `refObject`, `domNode`) that are only useful at development time and are stripped in production. These serve the same purpose as TypeScript types.

### Current Architecture

- **162 source files** import `PropTypes` from `prop-types`
- **163 source files** have `.propTypes = { ... }` assignments (some files have multiple)
- **133 source files** import and use `customPropTypes` from `src/lib`
- **`babel-plugin-transform-react-remove-prop-types`** strips all PropTypes in production builds
- **`babel-plugin-transform-react-handled-props`** generates `Component.handledProps` arrays from `propTypes` keys at build time
- **`getUnhandledProps(Component, props)`** reads `Component.handledProps` to determine which props to forward to the underlying DOM element
- **213 `.d.ts` files** already contain TypeScript interfaces for all component props

### Critical Dependency: `getUnhandledProps`

The `getUnhandledProps` utility at `src/lib/getUnhandledProps.js` is the most critical downstream consumer of PropTypes. It reads `Component.handledProps` (an array of prop names generated by `babel-plugin-transform-react-handled-props` from the `propTypes` keys). This mechanism must be preserved or replaced.

Current implementation:

```javascript
const getUnhandledProps = (Component, props) => {
  const { handledProps = [] } = Component
  return Object.keys(props).reduce((acc, prop) => {
    if (prop === 'childKey' || prop === 'innerRef') return acc
    if (handledProps.indexOf(prop) === -1) acc[prop] = props[prop]
    return acc
  }, {})
}
```

After PropTypes removal, `handledProps` must come from one of:
- Explicit static `handledProps` arrays declared in each component file
- Continued use of `babel-plugin-transform-react-handled-props` (if it can work without PropTypes)
- A build-time TypeScript transformer that generates `handledProps` from prop interfaces

### Task 12: Verify backward compatibility for consumers

12.1. **Breaking change notice.** Removing PropTypes is a breaking change for consumers who:
- Read `Component.propTypes` at runtime
- Use PropTypes-based tools (e.g., Storybook's auto-generated controls from PropTypes)
- Rely on development-time PropTypes warning messages

12.2. Document this breaking change in the CHANGELOG and migration guide:

```markdown
## Breaking Changes

### PropTypes Removed
All runtime PropTypes validation has been removed. Type checking is now handled
exclusively through TypeScript. If you were relying on PropTypes warnings in
development, use TypeScript for compile-time type checking instead.

The `Component.propTypes` static property no longer exists. If you were reading
it programmatically, use the TypeScript type definitions instead.
```

## Notes for AI Agents

- **This is the single largest phase by file count.** 163 source files must be modified. Process them in batches by directory (addons, collections, elements, modules, views) and commit each batch separately.
- **The `handledProps` strategy is the most critical decision.** Before removing any PropTypes, ensure that every component has a `handledProps` array. The recommended approach is to run a script that extracts the keys from `propTypes` before deleting the blocks.
- **Preserve JSDoc comments.** Many `propTypes` blocks contain the only documentation for props. Before deleting, verify that equivalent JSDoc comments exist in the corresponding `.d.ts` file. If they do not, add them.
- **Test files will break.** Many tests assert on PropTypes warnings (e.g., "Warning: Failed prop type: ..."). These assertions must be removed or rewritten. This is expected and should be done as part of this phase or deferred to Phases 18-24.
- **The `customPropTypes.suggest()` validator** is used by `Icon` and other components to provide "did you mean?" suggestions for invalid prop values. This development-time UX will be lost. Document this in the migration guide.
- **`react-is` dependency.** After removing `customPropTypes.js`, the `react-is` package is still needed by `factories.js` (for `ReactIs.isValidElementType`). Do not remove it from `dependencies`.
- **Order of operations within this phase:** (a) Generate `handledProps` arrays first, (b) Verify `getUnhandledProps` works with explicit arrays, (c) Then remove PropTypes in batches, (d) Remove build plugins last.
- Watch for `Component.defaultProps` patterns in `factories.js` -- the `defaultProps` option in `createShorthand` is a configuration object, not React's `Component.defaultProps`, so it is unaffected.
- The `eslint-disable react/prop-types` comments in `factories.js` (lines 75 and 146) should be removed as cleanup.
